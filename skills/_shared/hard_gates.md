# Hard Gates

Shared enforcement text for the automatic-reject gates and the black-box severity scale used across generation, hardening, solving, formatting, checking, and submission. Every skill that references this file must treat each rule below as a **HARD GATE**: a violation blocks the skill's own output (redesign, stop, or Critical finding, per that skill's own Hard Rules), not a style suggestion. This file exists to avoid repeating the same ~150 words of gate text in every skill; consult it directly rather than trusting a paraphrase.

## By-Hand Solution Gate

The intended official solution must be fully by hand and reviewer-checkable. Every core computation that contributes to the final answer must include intermediate calculations; do not hide coefficient extraction, matrix multiplication or inversion, enumeration, recurrence evaluation, exact arithmetic, or symbolic simplification behind "by computation", "one checks", "direct calculation gives", "computed similarly", or "applying the same formula". No external computational software, CAS, Python, exhaustive search, numerical oracle, calculator, calculator-dependent arithmetic, or code-only derivation may be required to obtain the answer. Code may only sanity-check a result already derived in the written solution.

**Citation carve-out (do not over-apply the anti-black-box rule).** This gate forbids hiding the problem's *own decisive step*, not every standard tool used around it. A genuinely standard, named, textbook result — a discrete-to-continuum spectral-convergence / min-max theorem, Rellich compactness, a named inequality, a classical structure theorem — may be **invoked by name with a brief verification of the hypotheses this problem needs**, rather than re-proved from scratch. That citation is Level-1 acceptable compression, not a black box. It becomes a black box only when the cited result *is* the problem's novel decisive step (see Probe P4). Conversely, re-deriving standard machinery at length inside one step is itself a reviewability reject (see the Mechanical-Bookkeeping Reject below): reserve explicit step-by-step derivation for the problem's own discovery; cite-and-check-hypotheses for everything standard around it.

**Do not over-apply the carve-out to a nontrivial leap wearing a theorem's name (Compressed-Rigor tell, Level 2/3).** A one-line invocation of named advanced machinery that performs the problem's *own* nontrivial deduction — "by a decomposition-group argument the residue extension at a prime over `(t-1)` realizes the full splitting field of `h`", "specializing `H_t` at `t=1` preserves the Galois group by Dedekind/genericity", "lift by Hensel's lemma" without naming the henselization/completion the lift lives over and the chosen valuation extension — is **not** a citation carve-out; it is a hidden nontrivial step. The tell: the sentence names a theorem but a peer reviewer cannot reconstruct *why it applies here* from the surrounding text (which specialization, which prime, which valuation, why the hypotheses hold). Such a step must be **justified explicitly** (state the henselization/completion, choose the valuation extension, exhibit the specialization and its unramified prime) — and if that honest justification would explode into tabulated modular arithmetic (the Mechanical-Bookkeeping Reject), the mechanism is too technical to present within the format: redesign, do not paper over it either way.

## Hand-Solvable Magnitude Bounds

The problem must be solvable by hand without a calculator or computer. Do NOT use numbers larger than `10^{15}` or smaller than `10^{-10}`; do NOT require computations that are unreasonable by hand (e.g. evaluating `\sin(5)` or `e^{-3}` numerically); do NOT require implementing an iterative algorithm or writing code to obtain the answer.

## Reasoning-vs-Computation Ratio (Too-Computational Reject)

The By-Hand and Magnitude gates above test whether the work is *possible* by hand. This gate tests whether the problem is *mostly* computation — the portal rejects a submission as **Too Computational** when its decisive content is arithmetic volume rather than reasoning, **even if every step is hand-feasible and both length gates pass**. Calibrated anchors from the Rainier guidelines' own worked examples:

- **Acceptable**: inverting a `6×6` matrix by hand (unpleasant, error-prone, but feasible); a single determinant / Smith-normal-form / linear-solve as the **closing** step of a problem whose difficulty lives in a prior discovery, when it is owned with a reviewer-checkable certificate (e.g. an LGV determinant behind a finite audit table — see "Own the Computation; Never Hide It" in `skills/_shared/passed_exemplars.md`); heavy-but-writable-out computation that requires no iterated algorithm.
- **Rejected**: ~2000 arithmetic operations on numbers up to ~`32000` (e.g. 127 candidate pairs, each run through 17 discriminant checks); "evaluate the recurrence for `N = 1, 2, …, 2025`"; 65 large linear-system solves (a `13×13` Lyapunov solve per candidate) then 65 eigenvalue extractions; exhaustive backtracking or enumerating ~`15000` permutations by direct scan; any core step that is only reasonably done by code / CAS.

Decisive test: strip the high-level vocabulary and state the decisive step in one plain sentence. If it is "run this computation `K` times" for large `K` — or if the **entire** decisive content is "solve a linear system / take a determinant / run Smith normal form / run the recurrence / enumerate the small state set" with no prior discovery needed to set it up — the shell is a *generator*, not difficulty, and the problem reads as Too Computational regardless of hand-feasibility. The tell fires only when that operation **is** the decisive step; a single such operation owned as the closing move of a problem gated elsewhere is fine (that is the "own the computation" case, not this reject). Redesign so the gate is a **discovery the computation cannot start without** (a hidden invariant, a limit/asymptotic, a general law over a free parameter). This is the portal-reject-category form of the Computational-volume-inflation and Shell-as-Computation-Generator failure modes (see `skills/_shared/passed_exemplars.md` and Probe P2/P4 in `skills/_shared/triviality_probe.md`). Enlarging the fixed instance does **not** fix it — it makes the human reach for code while the machine still grinds.

## Mechanical-Bookkeeping Reject (statement and solution)

Distinct from the Too-Computational and Self-containedness gates above, which fire on the *quantity* of operations. This gate fires on the *character* of the decisive content: a submission is rejected when its apparent difficulty is carried by **visible mechanical bookkeeping** rather than a compact conceptual argument — even when every step is shown, hand-feasible, and both length gates pass. This is a standing Rainier reviewer reject reason, quoted from real feedback: "long coefficient-carrying and repeated termwise manipulation that should fail"; "long list/table carried across multiple steps that the rubric says should FAIL"; "mechanical bookkeeping rather than genuine reasoning." Engineering volume is not difficulty — the same feedback that flags these also flags the item as "not sufficiently difficult."

Solution-side tells (any one → redesign, not reformat):
- a large auxiliary matrix introduced only to be ground through (e.g. a printed 4×4 with multi-digit entries), plus a coefficient/trace table of term-by-term formulas such as `b_{22}-2b_{23}+8b_{24}+2b_{33}-6b_{34}+17b_{44}` repeated across many rows;
- key identities (conjugation, composition) verified by a printed table of coefficient vectors ("the coefficient vectors provide the identities used here") rather than by an argument;
- an exhaustive finite-data certificate as the core construction: explicit edge/ribbon pairing lists (`(0,2)(1,8),(1,9)(0,1),…`), full orbit/vertex decompositions (`Q_1,…,Q_8`), per-case involution and cycle decompositions, determinant tables, "complete zero-location tables," six-case pair tables;
- an **irreducibility / primitivity certification by tabulated modular arithmetic** — a Frobenius / repeated-squaring remainder table `x^{p^k} \bmod f` across successive `k`, chained gcd or Bézout-identity computations mod several primes (mod 7 and mod 13, mod 29, …) to certify a polynomial is irreducible or a field degree is full. This is a term-after-term arithmetic grind standing in for a conceptual irreducibility argument (a ramification, Newton-polygon, or reduction-mod-one-good-prime argument);
- an **order-by-order / subgroup case table** — walking a Galois or automorphism group "case by case" through its subgroup lattice, or matching a product's `x^k` coefficient across all `k` via a fixed printed rule (`coeff of x^k = b_{k-2}-2r b_{k-1}+3 b_k`) row after row: coefficient-certificate and exhaustive-case tables both fire here even when each row is individually short.

Statement-side tells (any one → redesign the prompt):
- the statement is dominated by large raw symbolic-data blocks — several big vectors/matrices with entries built from the parameters, or an iterated composition (`C = A∘A∘A∘A∘B`) — that merely encode a simpler underlying object (a complex-power map, a single quadratic form); the layering is data, not mathematics;
- a max/min over several weighted quadratic forms, or several concatenated classification/counting subproblems, whose only role is to front-load coefficients or cases the solution must then bookkeep (this is also the horizontal-expansion / Probe P7 breadth failure — see `skills/_shared/triviality_probe.md`).

**The reconciliation that matters — do not resolve this the wrong way.** The By-Hand / Black-Box gate forbids *hiding* the derivation behind "one checks"; this gate forbids *dumping* it as a giant visible table. The two are not in tension: the fix for a solution that fails this gate is NEVER to hide the table (that trips the Black-Box scale) and NEVER to print it bigger or cleaner (that stays here) — it is to **redesign the problem** so the decisive step has a compact conceptual certificate (a gap identity, a hidden invariant, a quotient + correction, a short active/slack or orbit-stabilizer argument). If no honest write-up of the current mechanism avoids the carried table, the mechanism is too computational for the format — replace it (Harden-or-Replace), do not fake compactness.

Treat a violation at the same severity as the other automatic-reject gates: a **Critical** finding in `math-check`, and a redesign/replace trigger in `math-clone`/`math-harder` before the problem is saved.

## Smokescreen / Reverse-Engineered-Difficulty Reject

Distinct from the Mechanical-Bookkeeping and Too-Computational gates (which fire on the *form* of the work) and from Probe P2/P6 (decoration that strips away / a leaked route). This gate fires when the problem's difficulty comes from **uncovering the real problem from a disguised, obviously reverse-engineered set-up** rather than from the mathematics itself. It is a standing Rainier reviewer reject reason, quoted from real feedback: "please avoid hiding the real problem behind a smokescreen; difficulty should not come from having to uncover the actual problem from a set-up that was obviously reverse-engineered"; "the task hides a specially engineered balanced-word construction behind several layers of numerical-analysis notation — that's not behavior we encourage."

Tells (any one → redesign the prompt, do not merely re-notate):
- the setup wraps a simple or standard underlying object in **notation borrowed from another area** whose only function is concealment — numerical-analysis / integrator notation around a combinatorial word construction, measure-theory or operator dressing around a finite computation, an iterated-composition costume around a single power map. Test: strip the dressing and state the core in one plain sentence; if the core is elementary/standard and the layering carried no mathematics, the layering was a smokescreen.
- the "aha" the solver must have is **recognizing the disguise / decoding the encoding**, not making a mathematical discovery — the challenge is reverse-engineering how the statement was built, not solving what it asks.
- the target or constants were transparently **computed from the intended answer and then re-encoded** so that the task is to invert the encoding (this is the reverse-engineered-target failure mode in the response archive; here it is rejected on craft grounds even when it is not a P6 leak).

The fix is to make the difficulty **intrinsic**: pose the object directly, in the standard vocabulary and notation of its own Domain/Sub-domain (`skills/_shared/taxonomy_slots.md`), so the solver spends effort on the mathematics rather than on decoding a bespoke wrapper. This gate is tightly coupled to Probe **P8** (terminology-density and the taxonomy-vocabulary rule in `skills/_shared/triviality_probe.md`): invented notation and off-domain dressing are the raw material of a smokescreen, so keeping notation standard and minimal removes the failure at its source. Treat a violation at the same severity as the other automatic-reject gates: a **Critical** finding in `math-check`, and a redesign trigger in `math-clone`/`math-harder` before the problem is saved.

## Self-Containment Gate

A statement is rejected as **not self-contained** when it uses a symbol, operator, or custom term that is not defined, is defined only over a narrower domain than it is later applied to, or admits more than one defensible reading. This is a recurring Rainier reviewer reject reason, quoted from real feedback: "In Step 2, `R(w)` is defined only for `F(w)`, but the solution later uses `R(F(w)^c)`; please define `R(B)` for any board `B`, then set `R(w)=R(F(w))`"; "for strict self-containment, define 'edge-side' explicitly as one dart occurrence in a boundary walk — your interpretation is natural, but others are also defensible"; "the prompt is not fully self-contained — you do not define the signed implicit-midpoint substep; state the exact updates for `x` and `y` during a substep of size `ch`."

Procedure (a semantic coverage check, beyond LaTeX-syntax normalization — run design-time on the statement and the requested-answer notation):
- **Symbol/term inventory.** List every symbol, operator, named predicate, and custom term that is *used* anywhere in `problem.md` (including inside the requested answer), and every one that is *defined*. Every used item must be defined **before first use** and over the **entire domain** on which it is later applied — the `R(B)` case fails because `R` is defined on `F(w)` but applied to `F(w)^c`.
- **Ambiguity check.** For each custom term, ask whether a competent reader could give it a second defensible reading ("edge-side", "signed implicit-midpoint substep", an update rule stated only by name). If so, pin exactly one reading with an explicit definition — a natural interpretation is not a defined one.
- **Operational completeness.** If the statement invokes a process or substep (an integrator substep, an iteration, a construction), the exact update/rule must be written out, not referred to by name.

Fail action: add the missing definition / disambiguation / explicit rule before emit. Treat a violation at the same severity as the other automatic-reject gates: a **Critical** finding in `math-check`, and a redesign/repair trigger in `math-clone`/`math-harder` before the problem is saved. Keeping bespoke terms minimal and standard (Probe **P8**) shrinks this surface — fewer invented objects means fewer definitions that can be missing or ambiguous.

## No "Does Not Exist"

The answer must be a concrete object. `"Does not exist"` / `DNE` is **not a valid answer** on this project; if the intended answer is DNE, redesign so a concrete object is forced.

## No Obscure / Niche Topics

Do not rely on specialist objects identifiable only by name. Disallowed examples named explicitly — **Rolfsen tables, Alexander polynomials, Gromoll-Meyer spheres**, and the like. Build any needed object from curriculum-level definitions inside the statement instead (see `skills/_shared/frontier_authoring_guide.md`).

## Answer Length Gate

Effective from this project's 2026-07-14 Rainier workflow update: the final Answer must be **under 100 characters**, counting every character except `$` and whitespace (spaces, newlines, tabs). The in-app Evaluation Check LaTeX button now validates this length directly and returns any answer at or over the limit for revision — this is a HARD GATE, not a style preference.

**What to count**: the answer object itself — exactly the string that goes in the `## Answer` field, which is the content *inside* `\boxed{...}` with the `\boxed{` prefix and its closing `}` removed. Do **not** count the `\boxed` wrapper; the in-app button validates the Answer field, which never contains it. Counting `\boxed{X}` instead of `X` adds a spurious 8 characters and can wrongly fail a borderline answer.

To check it: take the `## Answer` string (or equivalently the inside of `\boxed{...}` from the final solution step), strip every `$` and every whitespace character, then count what remains — LaTeX command names, braces, digits, operators, commas, and every other symbol all count. Report the exact count, not an estimate.

**Grandfather clause (portal bookkeeping only — never an escape hatch for any skill)**: a problem already **ACCEPTED** before the announcement (or in a later finalized state — READY_TO_DELIVER, DELIVERED — that only follows acceptance) keeps that status even if its answer is at or over 100 characters; the portal does not retroactively reject it. That is the entire scope of the clause: it describes already-finalized, untouched work sitting in the portal. It is **not** a reason for any skill to let a long answer through. The moment such a problem is revised, reopened, re-solved, reformatted, or otherwise edited, it **loses the grandfather** and must satisfy the under-100 limit like any new problem. **Nothing pasted into a skill** — to author, harden, solve, normalize, reformat, check, or submit — **is ever grandfathered**: every problem that passes through a skill, regardless of prior status, must be under 100 characters. A long-answer problem is no longer eligible for acceptance regardless of mathematical quality.

**Design consequence**: `skills/_shared/frontier_authoring_guide.md`'s preference for rich bonus Answer Types (Matrix, Vector, Tuple or ordered list, Set or multiset of objects, Polynomial or rational function, Function or mapping, Canonical form) over a bare scalar still holds, but only when the concrete final object — written out in full, with every symbol expanded and no shorthand aliases — honestly fits under 100 characters. Favor a few small or parametrized entries (e.g. a $2\times2$–$3\times3$ matrix with short entries, a length-3–4 vector, a small finite set, a low-degree polynomial with few nonzero terms) over large or dense objects (e.g. a $5\times5$ matrix of multi-term rational entries, a 6+ component vector, a high-degree polynomial with many nonzero coefficients) — the latter now usually cannot fit the limit. Catch this at design time (`math-clone`, `math-harder`, `math-change-answer-type`), not as a surprise failure at `rainier-submit`. For a per-Answer-Type character-count feasibility table, worked count examples, and the list of length-risky types to sanity-check before choosing them, see **Answer Length Feasibility** in `skills/_shared/frontier_authoring_guide.md` — and note that most bonus types fit easily, so length is never a reason to retreat to a bare scalar.

## Answer Compaction Gate

A *compaction step* is any design step that reduces a rich derived object to a shorter final answer so it fits the Answer Length Gate. Compaction is acceptable only if **all four** conditions hold:

1. **No side-door**: the compacted value is unobtainable without first correctly deriving the full underlying object — cross-check against the P4 (core-reduces-to) and P5 (side-channel recoverability) tests in `skills/_shared/triviality_probe.md`.
2. **Error-sensitive**: a wrong component in the underlying object is very unlikely to still produce the correct compacted value — no cancellation or averaging-out of mistakes.
3. **Uniquely reviewer-checkable**: the single compacted answer can still be verified end-to-end by a reviewer, per the existing single-explicit-answer rule.
4. **Natural operation on one object**: the compaction is a standard operation on ONE object (evaluation at a point, trace, determinant, one coefficient), not an ad hoc combination of separately-posed sub-answers invented only to shorten text. "One object" means an object **well-defined by the problem's stated conditions** — it may be one the solver must *construct*; the statement is **not** required to, and should not, spell out its construction. If compacting forces the statement to define machinery (an iteration, a recipe, an auxiliary object) that a direct question about the object would not need, that added definition is a route leak, not a valid compaction: redesign the requested output (via `math-change-answer-type`) or choose a naturally short direct answer instead. This is checked by Probe P6 (Route-Concession Test) in `skills/_shared/triviality_probe.md`.

If any condition fails, treat it at the same severity as the other automatic-reject gates in this file: a **Critical** finding in `math-check`, and a redesign trigger in `math-clone`/`math-harder` before the problem is saved. The named approved and discouraged compaction techniques live in `skills/_shared/frontier_authoring_guide.md` (Answer Compaction Patterns); consult them at design time.

## Solution Length Gate

Effective from this project's 2026-07-19 Rainier workflow update: the solution's **Steps must total under 10,000 characters**. Only the step content counts.

**What to count**: every character of the `## Steps` section of `solution.md` — from just after the `## Steps` heading to the start of the next `##` section — exactly as written: prose, LaTeX commands, math, digits, spaces, and newlines all count. Do **not** count anything outside that section: the `## Answer` field, `## Solution Concepts`, `## Classification`, any `## Remark` or verification/audit sections, or their headings. Report the exact count (e.g. via `wc -c` on the extracted section), not an estimate.

**Interaction with the black-box rules (both gates must hold simultaneously)**: never satisfy this gate by re-hiding derivations behind "one checks", "by computation", or any Level 2/3 black box — the Black-Box Severity Scale below still applies at full strength. Legitimate compression means tightening prose, merging redundant algebra, and replacing page-long case grinds with certificate-style arguments (a gap identity, an active/slack table, a quotient + correction); it never means deleting reasoning a reviewer needs to check the answer.

**Design consequence (the operational form of the Self-containedness explosion failure mode)**: if an honest, black-box-free write-up of the intended solution cannot fit in 10,000 step-characters, the problem is too computational for the format — redesign toward a compact certificate rather than a long printed audit table. Catch this at design time (`math-clone`, `math-harder`): before committing to a mechanism whose verification needs large tables or many repeated expansions, sketch the expected Steps length. As with the Answer Length Gate, already-ACCEPTED/DELIVERED problems sitting untouched in the portal are not retroactively affected, but **everything that passes through a skill** — authored, hardened, solved, reformatted, checked, or submitted — must comply.

**Reviewability ceiling (softer than the hard cap, but real)**: 10,000 characters is the hard gate, not a safe target. The Rainier guidelines state that *excessively long solutions may be sent back for revision solely on the basis of length* — a human reviewer must be able to check every step, so a solution that is technically under 10,000 characters yet exhausting to review can still be bounced. Treat *well* under the cap, closed by a compact certificate, as the real target; do not aim for 9,999. If the honest write-up crowds the cap, that is a design signal to simplify the mechanism, not to tighten prose until it barely fits.

## Black-Box Severity Scale

Apply this three-level classification whenever auditing a solution for black-box reasoning (asserted logical transitions, computations, classifications, or enumerations whose correctness is not reconstructible from the written text):

| Level | Name | Description |
|---|---|---|
| 1 | Acceptable Compression | Routine algebraic simplifications or standard manipulations omitted for brevity but reconstructible without conceptual difficulty |
| 2 | Hidden Nontrivial Step | Omitted reasoning involving meaningful counting arguments, structural reductions, invariant-factor analysis, nontrivial combinatorics, or intermediate deductions that materially affect the proof |
| 3 | Critical Black Box | Core logical steps, deep theorem applications, exact enumerations, classification arguments, or key structural conclusions asserted without proof, mechanism, or verifiable derivation |

**Indicators to scan for:** unexplained exact counts, unsupported structural claims, hidden classification arguments, omitted derivations, abrupt jumps in difficulty or reasoning depth, vague phrases such as "clearly," "obviously," "it is easy to see," "by symmetry," "routine computation," "one can show," "a direct calculation gives," "by inspection," "it follows that," "one can verify," theorem invocations without checking assumptions, conclusions stronger than what the preceding reasoning establishes, and exact enumeration/classification/asymptotic/extremal/probabilistic-independence/quotient-structure/automorphism-counting claims that directly produce the final answer. **Reviewer-fillable-gap tell (Level 2):** any asserted step whose justification a reviewer could reasonably request in one or two sentences ("why does this hold here?") is a hidden nontrivial step — fill the short justification in the solution's own voice before submit rather than shipping it bare; this "fill in a few short justifications" request is the single most common minor-revision bounce of an otherwise-strong submission.

**Software-only final evaluation is Level 3** whenever the requested answer depends on it: a recurrence, transfer matrix, dynamic program, character/sign filter, finite search, or coefficient extraction is not a self-contained derivation if the final vector, polynomial, or number is merely stated after the procedure — phrases such as "running the recurrence gives", "the dynamic program yields", "the transfer matrix gives", "the sign filter evaluates to", "a computer calculation gives", or "expanding the coefficient extraction gives" mark this. Verification code is allowed only after a hand-auditable derivation already exists.

**Action by severity** (the calling skill's own Hard Rules decide the exact consequence — audit-and-report, expand-before-proceeding, or restart):
- Level 1: acceptable, no change required.
- Level 2: expand the step with the missing reasoning, or flag it if the skill is read-only.
- Level 3: treat as a verification failure or a blocking/Critical finding — do not paper over it with a black-box-audit note.

## No Auto Word-Wrap

Do not hard-wrap prose lines in `problem.md` or `solution.md` at a fixed column width. Uniform, machine-wrapped line breaks are a common LLM-detection tell. Let paragraphs run as natural long lines (or wrap only at genuine semantic breaks a human writer would choose), the same way the rest of this repo's markdown is written.

## Plain Portal Text Gate

The portal-bound problem statement and worked-solution Steps must never contain Markdown emphasis such as `**...**`, `__...__`, or `*...*`, and must not use blockquotes for labels or warnings. Write ordinary prose and LaTeX only. This rule targets the mathematical text pasted into the portal; required file headings, separators, and taxonomy-table structure may remain outside those fields.

Numbered or bulleted lists are allowed when they make a genuine mathematical enumeration clearer. Keep consecutive list items directly adjacent in the source, with no empty line inserted between items merely for visual spacing. Likewise, do not add blank lines just to make short definitions or conditions look more spacious. Use a blank line only at a real paragraph boundary or around display mathematics. `Step N:` remains the required solution-step label.
